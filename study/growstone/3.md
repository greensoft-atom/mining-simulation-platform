The engine and networking approach that your team can implement, debug and maintain most reliably is the stronger choice.

| Module          | Main responsibility                                            | Example operation   |
| --------------- | -------------------------------------------------------------- | ------------------- |
| Authentication  | Verify player identity and session                             | Sign in             |
| Character       | Load and update character state                                | Load character      |
| Mining          | Validate mining actions and calculate rewards                  | Claim mining result |

| Marketplace     | Manage listings and transfers                                  | Buy listing         |

| Payments        | Verify store purchases and grant entitlements                  | Redeem purchase     |
| Administration  | Inspect player state, audit transactions and investigate abuse | Review transaction  |

These modules can live in one backend codebase initially. Separating the code into clear modules does not require deploying every module as an independent service.

## 5.2 Example: how stone combination should work

Suppose a player selects two eligible stones and presses **Combine**.

The client should send a request containing the relevant item identifiers and a unique request identifier.

The backend should then:

1. Authenticate the player.
2. Check that the selected stones belong to that player.
3. Verify that both items are eligible for combination.
4. Check any required currency, level or other conditions.
5. Calculate the outcome using server-side rules.
6. Consume the input items and required resources.
7. Create the output item.
8. Record the transaction.
9. Return the result and updated inventory state.

All changes that must succeed together should be committed atomically.

If the client retries because of a connection timeout, the server should not consume the stones twice or generate two output items. A unique request identifier and persistent transaction record can make the operation idempotent.

This is one of the most important backend principles for a persistent game: **a network retry must not duplicate a reward or repeat a purchase**.

The same pattern applies to crafting, market purchases, reward claims and other valuable actions.

## 5.3 Example: how marketplace purchases should work

Suppose player A lists an item and player B buys it.

A secure implementation needs to coordinate:

- Listing status.
- Item ownership.
- Currency balance.
- The buyer's inventory capacity, if relevant.
- The seller's proceeds.
- Any applicable market fee.
- A persistent transaction record.

The operation should have one definitive result. Two buyers must not both successfully purchase the same listing, and a failed transaction must not leave the buyer without currency or the seller without the item.

The marketplace is therefore not just a frontend screen. It is a concurrency and transaction-processing problem.

That is why I would build the inventory and transaction foundation before enabling unrestricted player trading.

# 6. The backend security resources you should not skip

For a persistent MMORPG, security is part of the game design. If players can duplicate stones, fabricate rewards, manipulate currency or purchase items without paying, the economy can collapse.

These are the resources I would give your backend developer.

### Server authority

[Godot's multiplayer security guidance](https://docs.godotengine.org/en/stable/tutorials/networking/high_level_multiplayer.html) explains why clients should not determine important outcomes such as inventory, position or combat results. Unity's [server-authority documentation](https://github.com/Unity-Technologies/com.unity.multiplayer.docs/blob/main/docs/learn/dealing-with-latency.md) also explains how authority affects consistency and cheating. [Godot Engine documentation](https://docs.godotengine.org/en/4.7/tutorials/networking/high_level_multiplayer.html?utm_source=chatgpt.com)

**Apply this rule to your game:**

- The client may display a mining animation.
- The client may request a mining action.
- The server determines whether the action is valid and what rewards are earned.
- The client displays the confirmed result.

Never let the client simply announce that it earned a million coins or defeated a boss.

### Purchase verification

Google's official [Play Billing security guidance](https://developer.android.com/google/play/billing/security) recommends moving sensitive purchase logic to a backend, verifying purchase tokens, recording processed purchases and checking their legitimacy before granting entitlements. [Android Developers](https://developer.android.com/google/play/billing/security?authuser=101&utm_source=chatgpt.com)

This matters even if your initial game has only a few purchasable products. Build the entitlement and transaction model correctly before launch.

### Mobile security

The [OWASP Mobile Application Security Verification Standard](https://mas.owasp.org/MASVS/) provides a framework for reviewing authentication, local storage, cryptography, network communication and resistance to tampering. [OWASP Mobile Application Security](https://mas.owasp.org/MASVS/02-Frontispiece/?utm_source=chatgpt.com)

For your game, prioritize:

- Secure account sessions.
- Server-side authorization.
- No secrets embedded in the Android client.
- Rate limits on repeatable actions.
- Transaction logs for valuable items and currency.
- Server-side purchase verification.
- Administrative access controls.
- Backups and tested recovery procedures.

You do not need an enormous security team, but you do need these fundamentals before opening a competitive economy.

# 7. What we can learn about GrowStone's actual mechanics

The community sources provide some surprisingly specific historical information. Here are three examples worth following up.

## Example A: The eight-stone progression strategy

The old community guide recommends preserving a row of eight strong stones rather than combining every available stone immediately. Its explanation is that the player's effective damage pattern and farming efficiency can depend on maintaining a useful set of stones. [growstoneonline.fandom.com](https://growstoneonline.fandom.com/wiki/Guides_%28Old/Outdated%29?utm_source=chatgpt.com)

This suggests an important design possibility: stone combination may involve a trade-off between **concentrating power into fewer items and retaining several useful attacks or equipment slots**.

We should test that in the current game rather than assume the old guide still applies.

For your game, a similar strategic tension could work well if both options are viable:

- Combine items to gain a powerful attack or special effect.
- Keep several lower-tier items to gain versatility or sustained damage.

That is more interesting than making combination an automatic choice every time.

## Example B: Crafting uses several kinds of inputs

The community crafting page describes recipes involving materials such as cloth, iron, leather, boss drops, crystals and gold. It also records rarity probabilities for certain historical recipes. [growstoneonline.fandom.com](https://growstoneonline.fandom.com/wiki/Craft?utm_source=chatgpt.com)

This indicates that the game's progression is not solely about stones. It also has a resource and equipment economy.

For your game, that suggests a useful structure:

```text
Mining materials ──────┐
                       ├──> Crafting ───> Equipment
Monster drops ─────────┘                      │
                                              ▼
Stone progression ─────────────────────> Combat power
                                              │
                                              ▼
                                      Higher-tier content
```

You can extend this into a connected economy in which different activities produce different inputs.

## Example C: Item trading has restrictions

The historical marketplace guide documents item sealing as a prerequisite for selling certain items. [growstoneonline.fandom.com](https://growstoneonline.fandom.com/wiki/Item_Exchange?utm_source=chatgpt.com)

That is a potentially important economic control. Trade eligibility determines which items can flow between players, which items remain personal progression rewards, and which items can acquire market value.

Your own game should decide these rules before building a large marketplace. Changing tradeability after players have accumulated thousands of items can dramatically change prices and player expectations.

# 9. How we can make the research more precise

There is one thing I want to be transparent about: public research can tell us a great deal about GrowStone's features, history and reported player experiences, but it cannot provide a complete specification of the current game.

To create a genuinely useful reconstruction dossier, I suggest that we maintain a table like this:

| Feature                      | Evidence                                     | Current confidence                                       | What remains to be established                        |
| ---------------------------- | -------------------------------------------- | -------------------------------------------------------- | ----------------------------------------------------- |
| Stone mining                 | Official store listing and historical guides | High that the feature exists                             | Exact current mechanics and reward formulas           |
| Stone combination            | Official description and old community guide | High that combination is central                         | Current recipes, odds and edge cases                  |
| Crafting                     | Community wiki                               | High that a crafting system exists                       | Current recipes, costs and failure handling           |
| Marketplace                  | Community wiki                               | High that item exchange exists                           | Current eligibility rules and transaction behavior    |
| Clan system                  | Official description and community wiki      | High that clans and castle battles exist                 | Current permissions, rewards and battle rules         |
| Real-time synchronization    | Multiplayer features are advertised          | Feature existence is established, implementation unknown | Actual server topology and network protocol           |
| Database design              | No reliable public evidence identified       | Unknown                                                  | Must be designed independently                        |
| Backend programming language | No reliable public evidence identified       | Unknown                                                  | Must be designed independently                        |
| Current player population    | Public ratings and download tier             | Historical reach is evident; current activity is unknown | Reliable active-user data is not publicly established |
